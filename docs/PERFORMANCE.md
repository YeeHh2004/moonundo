# 实际工作负载与性能边界

MoonUndo 的泛型核心保存全量快照。浏览器增量编辑器可以用 `include_session: false` 避免每次编辑都复制和返回完整历史；需要保存时仍显式导出。这项优化不改变撤销、重做、事务或存档内容，也不是差量存储。

## 可复现测量

```sh
node scripts/build.mjs
node scripts/benchmark-workloads.mjs
# 可选：保存本机原始数据，不覆盖仓库里的参考记录
node scripts/benchmark-workloads.mjs --output dist/my-benchmark.json
```

如果尚无 dist 目录，先创建它，或把输出文件放在现有目录。测试只依赖 Node 和预编译引擎。CI 在 Linux Node 22 执行同一脚本并上传 `workload-benchmark` 产物；只检查两条路径的结果与恢复行为，不设置机器相关的耗时门槛。

每组预先构造 80 次未分组的真实修改，分别用“每次返回历史”和“按需返回历史”两种模式运行。两条路径各预热一次，再交替执行顺序收集三轮数据；每轮必须断言当前状态、时间线、完整导出存档相等，且新实例恢复后仍可撤销/重做。

编辑耗时包含 MoonBit dispatch 和宿主 JSON.parse；不包括预先生成输入或网页 DOM。存档导出和重新打开单独计时。原始记录还包含每轮 p95 编辑延迟、累计响应字节数及逻辑快照字节数。没有用进程内存占用推导库的内存上限。

## 本机参考结果

2026-09-30，Windows x64 / Node 24.19.0，固定 MoonBit compiler/core `0.10.14+7d59c7ec9`。下表为三轮的中位数，完整环境、引擎 SHA-256 和逐轮数据见 [原始 JSON](benchmark-workloads.json)。这是特定机器上的参考，不承诺所有设备或业务有相同结果。

| 工作负载 | 历史容量 | 返回全部历史：80 次编辑 | 按需导出：80 次编辑 | 最后一次响应：全部 → 按需 |
| --- | ---: | ---: | ---: | ---: |
| 100 条任务 | 10 | 153.08 ms | 28.03 ms | 115,578 → 10,408 bytes |
| 100 条任务 | 50 | 506.47 ms | 34.31 ms | 501,278 → 12,968 bytes |
| 500 条任务 | 10 | 2,177.49 ms | 301.88 ms | 585,978 → 49,608 bytes |
| 500 条任务 | 25 | 4,328.89 ms | 405.63 ms | 1,318,428 → 50,568 bytes |
| 嵌套文档：20 节 × 8 段 | 50 | 490.47 ms | 40.43 ms | 586,323 → 14,628 bytes |

两种模式在全部五组中产生相同的最终状态和历史，且每次导出均能重新打开。500 条任务、25 步容量的例子导出的恢复请求约 1,267,885 个 UTF-16 单元，低于 JSON 适配器 2,000,000 的限制。

## 如何选择容量

- `limit` 限制可撤销步数。最多保留 `limit + 1` 个已提交快照，另有当前状态副本，以及每层活动事务的起点副本。64 层事务上限不等于低内存开销。
- 泛型核心空间随快照大小、历史容量和事务层数增长。接入方负责深复制，若状态有大型嵌套数组或文档，要基于实际数据测量并降低容量。
- 增量编辑仍需要比较/复制当前状态，JSON 状态响应也仍包含当前完整状态和时间线。`record` 还会复制保留的历史引用数组；这里没有声称所有操作恒定耗时。
- JSON 适配器单次输入限制为 2,000,000 个 UTF-16 单元、64 层嵌套；历史积累后可能无法导出。导出拒绝不会修改当前状态，可先减小容量再导出。容量按步数限制，不是按字节。
- 一般网页编辑可先采用 20–50 步并开启 `include_session: false`。这只是起始配置，不能替代大数据与设备上的测量；需要大文档、协同或差量存储时应采用适合的状态模型。

旧的 [benchmark.mjs](../scripts/benchmark.mjs) 专门比较“不断回放整个操作列表”和“增量执行”的标量场景；它和本页的“增量模式中是否附带历史”是两个不同实验，不应混用结果。
